# Decisão e Priorização

Decidir bem não é acertar sempre. É tornar explícito o raciocínio, os critérios, os riscos e o próximo passo.

## Regra base

Toda decisão importante deve responder:

1. Qual problema está sendo resolvido?
2. Quais opções existem?
3. Quais critérios importam?
4. O que acontece se nada for feito?
5. A decisão é reversível?
6. Qual é o próximo passo mínimo?

## Matriz simples

| Critério | Pergunta |
|---|---|
| impacto | isso muda algo importante? |
| urgência | existe prazo real? |
| esforço | quanto trabalho exige? |
| risco | o que pode dar errado? |
| reversibilidade | dá para voltar atrás? |
| aprendizado | isso ensina algo útil? |

## Priorização 2x2

```txt
Alto impacto / baixo esforço  -> fazer primeiro
Alto impacto / alto esforço   -> planejar
Baixo impacto / baixo esforço -> fazer se sobrar energia
Baixo impacto / alto esforço  -> cortar ou adiar
```

## Decisão reversível vs irreversível

### Reversível

Pode ser testada rápido. Exemplo: mudar layout, testar biblioteca pequena, criar protótipo.

### Difícil de reverter

Exige mais cuidado. Exemplo: trocar stack principal, alterar modelo de dados central, assumir custo fixo alto.

## Anti-dispersão

Antes de começar algo novo, perguntar:

- isso ajuda o projeto principal?
- isso reduz dor real?
- isso gera entrega concreta?
- isso é curiosidade ou necessidade?
- existe algo mais importante esperando?

## Erros comuns

- decidir só pela empolgação;
- tentar otimizar tudo antes de validar;
- confundir urgência emocional com urgência real;
- manter projetos demais abertos;
- não registrar motivo da escolha;
- reabrir decisões já tomadas sem fato novo.

## Checklist rápido

- [ ] O problema está claro?
- [ ] Existe opção mais simples?
- [ ] O risco é aceitável?
- [ ] O próximo passo cabe em um dia?
- [ ] A decisão foi registrada?
- [ ] Existe critério de sucesso?
